# Weatherise Core Architecture v2

## 0. Updated File Structure and NVIDIA Full-Website Hosting

This section updates **V2 only**. It replaces the older MVP-style structure with the current implementation structure and factors in the deployment decision that the **full Weatherise website will be hosted on the NVIDIA hackathon infrastructure**.

The NVIDIA server is not only the model server. It is the full runtime host for:

- Frontend website
- Backend API
- WebSocket service
- LLM Parser
- Orchestrator Agent
- Context Agent layer
- Knowledge Base
- MCP Server
- RAG update pipeline
- Redis session/cache layer
- Vector database
- PostgreSQL structured storage
- NVIDIA NIM model runtime

The browser is only the client.

```text
Judge / User Browser
→ NVIDIA Server Public Port
→ Nginx Reverse Proxy
→ Frontend Website
→ FastAPI Backend
→ LLM Parser
→ Orchestrator Agent
→ Context Agent Layer
→ Knowledge Base + MCP Server
→ Intelligence Layer using NVIDIA NIM
→ Final Advice / Prediction
```

### 0.3 Runtime Request Flow on NVIDIA Infrastructure

```text
1. Judge opens the hosted Weatherise website:
   http://<team-server-ip>:<port>

2. Nginx receives the request and serves the frontend website.

3. User submits raw input from the website.

4. Frontend sends the request to FastAPI through `/api`.

5. FastAPI forwards raw input to the LLM Parser.

6. LLM Parser returns the initial JSON:
   - domain
   - intent
   - location
   - geographical_location
   - time_range
   - involved_context: []

7. Orchestrator Agent selects the correct Context Agent.

8. Context Agent fills `involved_context`.

9. Context Agent queries the Knowledge Base.

10. If required context is missing, Context Agent calls the MCP Server.

11. MCP routes retrieve missing context from external providers.

12. Reusable MCP results are passed into the RAG pipeline.

13. RAG pipeline updates the Knowledge Base.

14. Context Agent emits the fully processed JSON.

15. Intelligence Layer receives the fully processed JSON.

16. Intelligence Layer calls the NVIDIA NIM model runtime.

17. Intelligence Layer combines:
    - processed JSON,
    - Knowledge Base context,
    - MCP context,
    - real-time weather data,
    - user constraints.

18. Intelligence Layer returns advice, prediction, risk explanation, and final response.

19. FastAPI returns the result to the frontend.

20. Website displays the final result to the user.
```

## 1. Architecture Summary

Weatherise uses a **domain-aware multi-agent architecture**. The system first converts raw user input into a structured JSON object, then routes that object through an Orchestrator Agent into the appropriate Context Agent. The Context Agent fills the required context list, retrieves available context from the Knowledge Base, calls MCP routes for missing context, writes reusable new knowledge back through RAG, and finally sends a fully processed JSON object into the Intelligence Layer.

The corrected flow is:

```text
Raw User Input
→ LLM Parser
→ Orchestrator Agent
→ Domain Context Agent
→ Knowledge Base Retrieval
→ MCP Server for Missing Context
→ RAG Knowledge Update
→ Fully Processed JSON
→ Intelligence Layer
→ User Advice / Prediction
```

This architecture does **not** use NVIDIA Earth-2 Agent and does **not** use NVIDIA cuOpt. The Intelligence Layer is designed around NVIDIA NIM LLMs, prepared domain context, real-time weather retrieval, and prediction/recommendation logic.

## 3. Correct Runtime Flow

```text
1. User submits raw natural language input.

2. LLM Parser analyzes the natural language, situation, and implied context.

3. LLM Parser outputs an initial JSON object with:
   - domain
   - intent
   - location
   - geographical_location
   - time_range
   - involved_context as an empty array

4. Orchestrator Agent reads the parsed JSON and routes it to the correct Context Agent.

5. Context Agent fills the `involved_context` field based on the domain and intent.

6. Context Agent uses the involved context list to query the Knowledge Base.

7. Knowledge Base returns available context and reports missing context.

8. If required context is missing, MCP Server takes over and calls the correct MCP routes.

9. MCP routes retrieve missing data such as coordinates, places, time details, external domain data, or other required context.

10. Useful retrieved MCP information is stored back into the Knowledge Base through RAG.

11. Context Agent produces a fully processed JSON object.

12. Intelligence Layer receives the fully processed JSON.

13. Intelligence Layer pulls real-time weather data and any larger reasoning context needed for prediction.

14. Intelligence Layer produces the final advice, prediction, risk explanation, and user-facing response.
```

# 4. Component Responsibilities

## 4.1 User Input

### Responsibility

The **User Input** component is the external system boundary. It accepts raw natural language from the user.

At this point, the data is not structured. It may be incomplete, ambiguous, or informal.

### Example Inputs

```text
Plan a 3-day trip in Da Nang next week and avoid heavy rain.
```

```text
Is tomorrow safe for concrete pouring at this construction site?
```

```text
Should I irrigate my farm this week?
```

### Boundary

The User Input component only captures the request.

It does not:

- classify the domain,
- extract structured intent,
- retrieve knowledge,
- call MCP tools,
- perform prediction,
- generate final advice.

---

## 4.2 LLM Parser

### Responsibility

The **LLM Parser** converts raw natural language into the first structured JSON object.

It analyzes:

- the natural language request,
- the user situation,
- the requested action,
- the domain category,
- the location,
- the geographical location,
- the time range,
- the initial constraints.

The LLM Parser should **not** answer the user. It only prepares a structured object for routing.

---

### Parser Output Contract

The parser should output a JSON object like this:

```json
{
  "domain": "tourism",
  "intent": "travel_planning",
  "location": "Da Nang",
  "geographical_location": {
    "country": "Vietnam",
    "city": "Da Nang",
    "coordinates": null
  },
  "time_range": {
    "raw_text": "next week",
    "start": null,
    "end": null,
    "timezone": "Asia/Ho_Chi_Minh"
  },
  "involved_context": [],
  "user_constraints": [
    "avoid heavy rain"
  ],
  "raw_user_input": "Plan a 3-day trip in Da Nang next week and avoid heavy rain."
}
```

### Important Rule

At the parser stage:

```json
"involved_context": []
```

This field must remain empty until the request reaches the Context Agent layer.

Reason: the parser understands the user request, but the Context Agent owns domain-specific context selection.

---

## 4.3 Orchestrator Agent

### Responsibility

The **Orchestrator Agent** is the workflow routing component.

It receives the parser JSON and routes the request to the appropriate Context Agent based on:

- domain,
- intent,
- confidence score,
- required workflow type.

### Example Input

```json
{
  "domain": "tourism",
  "intent": "travel_planning",
  "location": "Da Nang",
  "time_range": {
    "raw_text": "next week"
  },
  "involved_context": []
}
```

### Example Output

```json
{
  "selected_context_agent": "tourism_context_agent",
  "routing_reason": "The request belongs to the tourism domain and the user wants travel planning.",
  "payload": {
    "domain": "tourism",
    "intent": "travel_planning",
    "location": "Da Nang",
    "time_range": {
      "raw_text": "next week"
    },
    "involved_context": []
  }
}
```

### Boundary

The Orchestrator owns:

- routing,
- workflow coordination,
- selecting the correct Context Agent.

The Orchestrator does not own:

- Knowledge Base search,
- MCP route execution,
- domain context filling,
- prediction,
- final advice.

---

## 4.4 Context Agent Layer

### Responsibility

The **Context Agent** is the domain-processing component.

It receives the structured JSON from the Orchestrator and fills the `involved_context` field.

There can be different Context Agents for different domains:

```text
Tourism Context Agent
Construction Context Agent
Agriculture Context Agent
```

Each Context Agent understands what data is required for its domain.

---

### Context Agent Output Example

For a tourism request, the Context Agent may transform this:

```json
{
  "domain": "tourism",
  "intent": "travel_planning",
  "location": "Da Nang",
  "involved_context": []
}
```

Into this:

```json
{
  "domain": "tourism",
  "intent": "travel_planning",
  "location": "Da Nang",
  "geographical_location": {
    "country": "Vietnam",
    "city": "Da Nang",
    "coordinates": null
  },
  "time_range": {
    "raw_text": "next week",
    "start": null,
    "end": null,
    "timezone": "Asia/Ho_Chi_Minh"
  },
  "involved_context": [
    "weather_forecast",
    "tourist_attractions",
    "indoor_outdoor_classification",
    "opening_hours",
    "travel_time",
    "weather_risk_rules",
    "backup_plan_options"
  ],
  "user_constraints": [
    "avoid heavy rain"
  ]
}
```

---

### Domain Logic Examples

#### Tourism Context Agent

The Tourism Context Agent knows that:

```text
Outdoor attractions require rain probability, wind speed, temperature, visibility, and heat risk.
Beach activities require rainfall, wind, storm risk, UV level, and temperature.
Indoor backup planning requires opening hours, location, attraction type, and travel distance.
```

#### Construction Context Agent

The Construction Context Agent knows that:

```text
Concrete pouring requires rainfall, humidity, temperature, and wind speed.
Crane operation requires wind speed and gust risk.
Outdoor worker safety requires heat index, rainfall probability, and storm warning.
```

#### Agriculture Context Agent

The Agriculture Context Agent knows that:

```text
Irrigation advice requires rainfall forecast, soil moisture, crop type, and temperature.
Disease risk requires humidity, recent rainfall, crop profile, and temperature range.
Harvest timing requires rainfall, field accessibility, and crop maturity window.
```

## 4.5 Knowledge Base

### Responsibility

The **Knowledge Base** stores reusable internal context.

After the Context Agent fills the `involved_context` field, it queries the Knowledge Base for the required context.

The Knowledge Base is used for context that is relatively stable, reusable, or already known.

### Example Stored Knowledge

```text
Da Nang attraction database
Indoor/outdoor classification of places
Opening-hour references
Tourism weather-risk rules
Construction safety thresholds
Agriculture crop profiles
Historical local knowledge
Domain documents
Previously validated external context
```

---

### Example Knowledge Base Query

```json
{
  "domain": "tourism",
  "location": "Da Nang",
  "required_context": [
    "tourist_attractions",
    "indoor_outdoor_classification",
    "opening_hours",
    "weather_risk_rules"
  ]
}
```

### Example Knowledge Base Response

```json
{
  "found_context": {
    "tourist_attractions": "...",
    "indoor_outdoor_classification": "...",
    "weather_risk_rules": "..."
  },
  "missing_context": [
    "opening_hours",
    "travel_time"
  ]
}
```

## 4.6 MCP Server

### Responsibility

The **MCP Server** is the external data and tool execution boundary.

It takes over when the Knowledge Base does not contain some required context.

The MCP Server exposes multiple MCP routes. Each route is responsible for retrieving one specific type of missing data.

### Architectural Flow

```text
Context Agent
→ identifies missing context
→ calls MCP Server
→ MCP Server selects MCP route
→ MCP route retrieves missing data
→ data returns to Context Agent
```

### Why MCP Server Exists

The MCP Server prevents domain agents from directly calling random external APIs.

This gives the system:

- cleaner integration boundaries,
- centralized tool control,
- easier debugging,
- safer permission management,
- easier replacement of API providers,
- better observability.

---

## 4.7 MCP Routes

### Responsibility

Each **MCP Route** retrieves a specific type of information.

Examples:

```text
location.resolveCoordinates
weather.getForecast
place.getOpeningHours
place.searchNearby
time.resolveDateRange
map.getTravelTime
domain.getExternalRiskData
```

### Example MCP Route Call

```json
{
  "route": "location.resolveCoordinates",
  "input": {
    "location": "Da Nang, Vietnam"
  }
}
```

### Example MCP Route Response

```json
{
  "route": "location.resolveCoordinates",
  "output": {
    "latitude": 16.0544,
    "longitude": 108.2022,
    "confidence": "high",
    "source": "geocoding_provider"
  }
}
```

### Design Rule

Each MCP route should do one job.

Good route:

```text
weather.getForecast
```

Bad route:

```text
getAllTravelWeatherMapAndTourismData
```

Small routes are easier to test, monitor, replace, and reuse.

---

## 4.8 Knowledge Base Update Through RAG

### Responsibility

After MCP routes retrieve missing information, useful new information can be stored back into the Knowledge Base through RAG.

This allows the system to learn reusable context over time.

### RAG Update Flow

```text
MCP Route Output
→ validate data
→ normalize data
→ chunk or structure the data
→ generate embeddings
→ store in vector database / knowledge store
→ attach metadata
→ make it available for future retrieval
```

### Example RAG Metadata

```json
{
  "domain": "tourism",
  "location": "Da Nang",
  "context_type": "opening_hours",
  "source": "place_mcp_route",
  "freshness": "dynamic",
  "created_at": "2026-06-09T10:00:00+07:00"
}
```

### Storage Policy

Not every MCP result should become permanent knowledge.

Store information when it is:

- reusable,
- source-traceable,
- validated,
- useful for future retrieval.

Highly volatile information, such as minute-by-minute weather, should usually be cached with expiration instead of stored as permanent knowledge.

## 4.10 Intelligence Layer

### Responsibility

The **Intelligence Layer** receives the fully processed JSON and performs final reasoning.

It uses:

- the processed JSON,
- domain context,
- Knowledge Base results,
- MCP-filled context,
- real-time weather data,
- larger reasoning context,
- suitable NVIDIA NIM LLMs.

### Intelligence Layer Internal Flow

```text
Receive fully processed JSON
→ inspect intelligence requirements
→ pull real-time weather data if required
→ combine domain context + live weather + user constraints
→ run reasoning through selected NVIDIA NIM LLM
→ generate prediction
→ generate advice
→ explain risk
→ return final user response
```

### Output Contract

```json
{
  "prediction": "Rain risk is high on Day 1 and moderate on Day 2.",
  "recommendation": "Move outdoor activities to the morning and keep indoor backups in the afternoon.",
  "risk_assessment": {
    "rain_risk": "high",
    "wind_risk": "medium",
    "trip_disruption_risk": "medium"
  },
  "explanation": "The recommendation is based on forecasted rain probability, activity type, and the user's constraint to avoid heavy rain.",
  "final_answer": "..."
}
```

# 5. Correct Data Ownership

| Component | Owns | Does Not Own |
|---|---|---|
| User Input | Raw request capture | Parsing, routing, reasoning |
| LLM Parser | Structured JSON extraction | Domain context filling, MCP calls, final advice |
| Orchestrator Agent | Routing to the correct Context Agent | Domain rules, Knowledge Base search, prediction |
| Context Agent | Filling `involved_context`, deciding needed context | Final user-facing advice |
| Knowledge Base | Stored reusable context | Live API execution |
| MCP Server | Controlled external route execution | Final reasoning |
| MCP Routes | Specific missing data retrieval | General orchestration |
| RAG Update | Learning reusable retrieved information | Real-time prediction |
| Intelligence Layer | Final reasoning, prediction, recommendation | Initial parsing and routing |

---

# 6. Key Architecture Decisions

## 6.1 Parser Does Not Fill `involved_context`

The parser only creates the initial structured request.

The field starts empty:

```json
"involved_context": []
```

The Context Agent fills it later because only the domain agent knows what context is required.

---

## 6.2 Orchestrator Is a Routing Component

The Orchestrator sends the parsed request to the correct Context Agent.

It should not perform deep domain reasoning or prediction.

---

## 6.3 Context Agent Controls Context Retrieval

The Context Agent decides:

```text
What context is needed?
What exists in the Knowledge Base?
What is missing?
What must be requested from MCP?
```

---

## 6.4 MCP Fills Missing Context

The MCP Server only takes over when required context is missing from the Knowledge Base or must come from a live/external data source.

---

## 6.5 RAG Updates the Knowledge Base

After MCP retrieves useful information, the Knowledge Base can learn the new information through RAG.

This improves future retrieval and reduces repeated external calls.

---

## 6.6 Intelligence Layer Receives Completed Context

The Intelligence Layer should not receive a raw user query.

It receives a fully processed JSON object with all available context already prepared.

This keeps the Intelligence Layer focused on prediction and recommendation instead of data discovery.

---

# 7. Final Architecture Rule

```text
Raw input belongs to the User Input layer.

Natural language structuring belongs to the LLM Parser.

Routing belongs to the Orchestrator Agent.

Context definition belongs to the Context Agent.

Stable context retrieval belongs to the Knowledge Base.

Missing external context retrieval belongs to the MCP Server.

Reusable new knowledge is written back through RAG.

Final reasoning, prediction, and advice belong to the Intelligence Layer.
```

This separation keeps the system clean, testable, scalable, and easier to present in the hackathon.
